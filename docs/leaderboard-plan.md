# 리더보드 계획

아직 만들지 않았다. 다만 지금 구조가 이걸 받을 수 있게 되어 있어서,
붙일 때 뭘 결정해야 하는지 미리 적어 둔다.

지금은 `wrangler.jsonc`에 `main`이 없어 **자산만 서빙하는 워커**다. 여기에
`main`을 추가하면 `/api/*`만 코드가 처리하고 나머지는 그대로 엣지에서 나간다.
정적 사이트를 통째로 다른 데로 옮길 필요가 없다.

---

## 1. 진짜 어려운 건 신원이 아니라 부정 방지

먼저 인정하고 갈 것: **클라이언트가 시간을 재는 게임에서 부정을 완전히
막을 수는 없다.** 브라우저 콘솔에서 이 한 줄이면 끝난다.

```js
fetch('/api/score', {method:'POST', body: JSON.stringify({error: 0})})
```

그러니 목표는 "완벽한 차단"이 아니라 **가벼운 부정은 귀찮게 만들고,
사람이 낼 수 없는 기록은 걸러내는 것**이다.

### 서버가 판을 열게 한다

지금은 클라이언트가 목표를 정하고 결과도 스스로 계산한다. 리더보드에
올릴 기록은 서버가 판을 열어야 한다.

```
POST /api/round        → { roundId, target, token, serverStartMs }
   token: roundId·target·발급시각을 HMAC으로 서명한 값

POST /api/score        { roundId, token, elapsed }
   서버가 검증:
     - token 서명이 맞는가 (위조된 라운드 거부)
     - roundId를 이미 제출했는가 (재사용 거부)
     - 발급 후 경과한 서버 시각 ≈ elapsed 인가
       (네트워크 지연만큼 여유를 두되, 3초 목표에 10초가 걸렸다면 거부)
```

이러면 "라운드를 열지 않고 점수만 던지기"와 "같은 라운드로 여러 번 제출"이
막힌다. 남는 구멍은 정직하게 라운드를 열고 자동화로 정확히 누르는 경우인데,
그건 아래 통계 필터가 잡는다.

### 사람이 낼 수 없는 기록 거르기

- 단발 기록은 운으로 0.001s가 나온다. **연속 N회 평균**을 순위 기준으로 쓴다.
- 평균 오차가 사람의 물리적 한계(반응 편차) 아래면 플래그. 실측 분포를
  좀 모은 뒤에 임계값을 정하는 게 맞다 — 지금 숫자를 박아 두면 근거가 없다.
- 같은 신원에서 비정상적으로 잦은 제출은 레이트리밋.

## 2. 신원: 로그인은 마지막 수단

틱톡에서 유입되는 게임에서 **로그인 화면은 이탈 지점**이다. 단계별로
올라가는 걸 권한다.

| 방식 | 마찰 | 신뢰도 | 비고 |
|---|---|---|---|
| 익명 기기 ID (localStorage UUID) | 없음 | 낮음 | 지우면 초기화. 캐주얼엔 충분 |
| 닉네임 + 기기 ID | 매우 낮음 | 낮음 | **1단계로 이걸 권함** |
| IP | 없음 | 낮음 | 아래 문제 |
| OAuth (Google/GitHub) | 높음 | 높음 | 정말 필요해질 때 |

**IP를 신원으로 쓰지 말 것.** 세 가지 이유다.

1. 모바일 캐리어 NAT 뒤에서는 수만 명이 같은 IP를 쓴다. 회사·학교도 마찬가지다.
2. IPv6는 프라이버시 확장으로 주소가 계속 바뀐다.
3. **IP는 개인정보다.** 저장하면 GDPR·개인정보보호법의 처리 근거·보관기간이
   따라붙는다. 순위표 하나 만들려고 질 부담이 아니다.

레이트리밋 용도로 IP를 *일시적으로* 쓰는 건 다르다. Cloudflare가 이미
`CF-Connecting-IP`를 주고, 해시해서 짧게만 들고 있으면 된다.

권장 1단계: **닉네임 + 익명 기기 ID**. 기기 ID는 첫 방문에 `crypto.randomUUID()`로
만들어 localStorage에 넣고, 서버에는 그 값의 해시만 보낸다.

## 3. 저장소

**Cloudflare D1**(엣지 SQLite)이 이 규모에 맞다. 무료 티어가 하루 500만 읽기
수준이라 한참 여유가 있고, 워커에서 바로 붙는다.

```sql
CREATE TABLE scores (
  id          INTEGER PRIMARY KEY AUTOINCREMENT,
  player_id   TEXT NOT NULL,        -- 기기 ID 해시
  nickname    TEXT NOT NULL,
  avg_error   REAL NOT NULL,        -- 세션 N회 평균 절대오차
  rounds      INTEGER NOT NULL,
  created_at  INTEGER NOT NULL
);
CREATE INDEX idx_scores_rank ON scores(avg_error ASC, created_at ASC);
```

순위표는 상위 100개만 자주 읽히므로 **KV나 Cache API에 30초쯤 캐시**한다.
D1을 매 요청 때리면 무료 티어를 금방 쓴다.

`Durable Objects`는 전역 순위의 강한 일관성이 필요할 때 쓰는데, 리더보드가
몇 초 늦게 갱신되는 건 아무도 신경 쓰지 않는다. 지금은 과하다.

## 4. 붙이는 순서

1. `wrangler.jsonc`에 `main: "src/worker.ts"` 추가. `/api/*`만 처리하고
   나머지는 `env.ASSETS.fetch(request)`로 넘긴다.
2. `/api/round`, `/api/score` — 서명 토큰 + 검증. **먼저 이걸 만든다.**
   저장 없이 검증만 있어도 구조가 잡힌다.
3. D1 바인딩 + `scores` 테이블.
4. `/api/leaderboard` + 캐시.
5. 프런트: 닉네임 입력(선택), 세션 종료 시 제출, 순위 표시.

1~2번까지가 설계의 핵심이고 나머지는 붙이는 작업이다.

---

## 5. 그 전에 정할 것

- **순위 기준.** 단발 최고 기록인가, N회 평균인가? 평균이 부정에 강하고
  게임도 오래 붙잡는다. N은 10회쯤이 적당해 보이는데 실측이 필요하다.
- **목표가 정수 2~9초로 고정된 게 여기서 유리하다.** 종류가 8개뿐이라
  기록을 서로 비교할 수 있다. 소수점 목표였다면 난이도가 제각각이라
  순위 자체가 성립하지 않았다.
- **닉네임 정책.** 중복 허용? 욕설 필터? 최소한 길이 제한과 제어문자 차단은
  서버에서 해야 한다.
- **보관 기간.** 무기한 쌓을 이유가 없다. 상위 N개 + 최근 M일 정도로 자르고
  나머지는 지우는 게 저장소와 개인정보 양쪽에 낫다.
